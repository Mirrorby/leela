# Лила (Leela) — цифровая версия игры-трансформации

Mobile-first веб-приложение, работает как обычный сайт (GitHub Pages) и как
Telegram Mini App на едином frontend.

## Статус

- ✅ Этап 1 — каркас репозитория и ruleset
- ✅ Этап 2 — Game Engine + unit-тесты
- ✅ Этап 3 — минимальный UI-каркас (14 экранов)
- ⬜ Этап 4 — Guest Mode + деплой
- ⬜ Этап 5 — SVG-поле и графика
- ⬜ Этап 6 — Telegram-обвязка на фронте
- ⬜ Этап 7 — Cloudflare Worker (API + бот)
- ⬜ Этап 8 — Telegram Mode целиком + финальная сверка

## Структура проекта

```
src/
  data/
    rulesets/classic-v1.json     — правила игры (доска, рождение, шестёрки,
                                     переходы). Версионируется отдельным файлом,
                                     старые версии не удаляются и не мигрируют.
    content/ru/cells.json        — тексты 72 клеток (сейчас заглушки,
                                     ждут финального контента)
  types/game.ts                  — TS-типы Ruleset, ContentPack, GameState
  game/
    ruleset.ts                   — загрузчик ruleset/контента по id
    gameEngine.ts                — ядро игровой логики (state machine).
                                     UI и Storage НИЧЕГО не знают о правилах
                                     и обращаются сюда за любым решением.
    diceEngine.ts                — генерация/валидация броска кубика
    transitionEngine.ts          — логика змей/стрел
  state/
    useGameSession.ts            — единственная точка входа UI в Game Engine
                                     (создание партии, броски, восстановление
                                     "что произошло" для экранов)
  navigation/
    types.ts                     — типы стека экранов (без react-router)
    flow.ts                      — куда вести после каждого события движка
    ScreenProps.ts                — общие пропсы для всех экранов
  screens/                       — 14 экранов этапа 3 (Splash, Intro,
                                     RequestInput, DiceModeSelect, GameHome,
                                     DiceRoll, TurnResult, CellCard,
                                     TransitionEvent, ExtraRollPrompt,
                                     TripleSixReset, History, FinishScreen,
                                     Summary)
```

## Game Engine (этап 2)

Реализован в `src/game/gameEngine.ts` как чистые функции без побочных
эффектов — движок не читает и не пишет ничего сам, только принимает
`GameState` + `Ruleset` и возвращает новое состояние + список событий:

- `createNewGame({ id, ruleset, request, diceMode })` — создать партию
- `canRoll(game)` — можно ли сейчас бросать кубик
- `processRoll(game, ruleset, value, clientEventId)` — обработать один бросок

Покрыт 12 unit-тестами из ТЗ (`src/game/gameEngine.test.ts`, `npm test`):
рождение по 6, обычный ход, змея, стрела, транзитный проход мимо перехода,
серия из 2 шестёрок, серия из 3 шестёрок со сбросом, точный финиш,
перелёт в диапазон 69–72, отклонение хода в FINISHED, идемпотентность по
`clientEventId`, независимость логики от режима кубика.

Важное архитектурное решение: рождение (бросок 6 из WAITING_FOR_BIRTH)
всегда закрывается как отдельный ход, даже если даёт дополнительный
бросок. Это сделано специально, чтобы тройная шестёрка сразу после
рождения не могла откатить игрока обратно в состояние "ещё не родился" —
такое поведение не описано в ТЗ и выглядело бы как баг для пользователя.


## UI-каркас (этап 3)

14 экранов без финальной графики поля — цель этапа была прогнать весь
пользовательский сценарий руками и убедиться, что Engine и UI стыкуются.
Навигация — собственный стек экранов в `App.tsx` (`useState<ScreenEntry[]>`
+ push/replace/pop/resetTo), react-router не используется, как и решили на
этапе 1.

`src/state/useGameSession.ts` — единственное место, где UI вызывает
`createNewGame`/`processRoll`. Экраны никогда не трогают Game Engine
напрямую. Здесь же живёт восстановление "что произошло за ход"
(`LastMove`: с какой клетки, куда приземлились до перехода, куда попали
после — нужно для экрана `TransitionEvent`, так как `RollEvent` из движка
не хранит номера клеток, только тип события).

`src/navigation/flow.ts` — вся маршрутизация после броска в одном месте
(`afterTurnResult` / `afterTransitionEvent` / `afterCellCard`), экраны не
дублируют знание о событиях движка. Проверено скриптом-симуляцией полного
прохождения партии (рождение с провалом, рождение с доп. броском, серия из
3 шестёрок с продолжением хода, точный финиш) напрямую через `gameEngine` —
цепочка экранов не рвётся ни на одном событии. Переход по змее/стреле
логически проверен компилятором, но не пройден вживую: в `classic-v1.json`
список `transitions` пока пуст (см. блокер ниже).

## Разработка

```bash
npm install
npm run dev       # локальный запуск
npm run build     # production-сборка в dist/
```

При пуше в `main` GitHub Actions (`.github/workflows/deploy.yml`)
автоматически собирает и публикует `dist/` на GitHub Pages.
