# Проверки и публикация схемы

Все GitHub Actions используют Node 24. Worker устанавливает npm 12 перед
`npm ci`, сохраняя существующий lock-файл. Проверки PR и выпуска используют
один reusable workflow `checks.yml`: тесты фронтенда, линтер и сборку;
проверку типов Worker, его тесты, тесты перехода со старой схемы, применение
SQL к новой локальной D1, повторное применение и сборку Worker без публикации.
PR не получает Cloudflare-секреты и не обращается к действующей базе.

`deploy.yml` запускается при push в `main` и вручную для `main`. После
успешных проверок вызывается `deploy-worker.yml`: миграции действующей D1,
деплой Worker и проверка `/api/v1/health`. Только затем публикуется собранная
игра в Pages. Изменение любого общего файла проходит этот же путь без
отдельного списка `paths`. Ошибка проверки, миграции или Worker останавливает
публикацию Pages. Уже действующая игра при этом остаётся доступной.

Worker и Pages имеют отдельные группы concurrency без отмены выполняющегося
деплоя. Старые очередные запуски проверяют SHA текущего `main` и пропускают
публикацию устаревшей версии. Worker повторяет эту проверку после миграций.
Новый коммит во время выполняющегося деплоя обслуживается следующим выпуском.
Защита ветки от прямого слияния настраивается отдельно в GitHub; эти workflow
сами ограничивают публикацию результатами проверок.

## Первое применение к старой базе

Схема проекта раньше создавалась вручную и частично — самим Worker. Поэтому
обычный `wrangler d1 migrations apply` без перехода способен повторить
`ALTER TABLE` уже существующей колонки и упасть. Для проекта используйте:

```bash
cd worker
npm ci
npm run migrate:local
```

`scripts/migrate.mjs` сначала читает только описание таблиц/индексов и журнал
`d1_migrations`. `legacy-baseline.mjs` проверяет замороженные миграции
0001–0016 по SHA-256 и строит копию фактической схемы в памяти без строк
игроков. В этой копии проверяются типы колонок, обязательность, значения по
умолчанию, первичные ключи, определения индексов и ограничение статусов
Tribute. Существующий столбец из исторического `ADD COLUMN` пропускается
только при совместимой структуре. Недостающие исторические таблицы,
индексы и колонки добавляются; несовместимая структура останавливает
переход до записи в действующую базу. Игры, балансы и покупки не
переписываются и не удаляются.

После успешной проверки выполняется только недостающий исторический DDL,
а миграции записываются в стандартный журнал Wrangler. Повтор безопасен,
включая частично выполненный старый переход. Новые миграции после 0016
применяет штатный Wrangler. Они не получают автоматическую отметку о
выполнении через переход. Если в базе уже есть миграция, отсутствующая в
этом checkout, выпуск останавливается. Файлы исторических миграций и их
контрольные суммы не меняйте; изменения схемы оформляйте новым файлом.

Для действующей базы тот же сценарий запускается в Actions:

```bash
npm run migrate:remote
```

Cloudflare-токен `CLOUDFLARE_API_TOKEN` должен иметь право изменения Workers
Scripts и D1 в аккаунте с базой `leela`. В PR этот токен не передаётся.
Не записывайте токен в репозиторий. В штатном выпуске ручной SQL не нужен.
Если переход остановился, сначала проверьте сообщение о несовместимой
структуре или права токена; не отмечайте все миграции выполненными вручную.

## Локальная проверка изменений схемы

```bash
npm run typecheck
npm test
npm run test:migrations
CI=true WRANGLER_SEND_METRICS=false npx wrangler d1 migrations apply leela --local --persist-to .wrangler/migration-check
npm run migrate:local
npm run migrate:local
npm run build
```

Первый SQL-прогон в CI использует новую локальную D1; тесты перехода
покрывают ручную и частичную схему с сохранёнными играми, платным балансом
и покупками, несовместимые колонки/индексы и повтор. `build` собирает Worker
с `--dry-run` и не публикует его. Каталоги `.wrangler/` и файлы `.dev.vars`
исключены из git. Новые миграции должны сохранять совместимость со старым
Worker, пока выполняется выпуск; восстановление предыдущего кода само по
себе не отменяет уже применённое изменение базы.
